01 — The Basics

What exactly is Hans?

Hans is not a chatbot you visit on a website. Hans is a persistent, always-running AI agent installed on dedicated hardware — like hiring an employee who never clocks out, never forgets, and costs a few hundred dollars a month.

💡

The core idea: Instead of asking an AI a question and getting a one-time answer, Hans has memory, tools, ongoing tasks, and access to real systems. He can read and write files, search the web, send Slack messages, run code, check email, manage a calendar, and execute background jobs on a schedule — all while maintaining context about the business across sessions.

💬

What most people think AI is

A chat window. You ask something, it answers. Session ends, everything is forgotten. No connection to your real tools or data. No follow-through.

🛠️

What Hans actually is

A persistent agent with memory, tools, and system access. He can send emails, write code, check on projects, set reminders, manage files, coordinate with team members via Slack, and wake up at 3 AM to run a scheduled task — then report back in the morning.

Right now, Hans is running on:

🖥️

A Mac mini

Apple Silicon, always on, sitting in a home office. Not a cloud server — real dedicated hardware. This is important for reliability and cost.

🌐

OpenClaw

The software framework that runs the AI agent. Think of it like an operating system for AI — it handles memory, tools, scheduling, and routing messages to the right AI model.

🧠

Claude (Anthropic)

The AI model that powers Hans's reasoning. Claude reads the context and memory files, then decides what to do and how to respond. Hans can switch models for different tasks.

03 — The Evolution

How Hans evolved

Hans didn't arrive as a finished product. He grew through real use, real failures, and real problems that needed solving. This is what that progression looks like.

Phase 1: Personal Assistant

The chatbot phase

Hans started as a smart question-answering tool. Matt would ask questions, Hans would research and answer. Calendar checks, email drafting, web searches. Useful but not yet transformative. Think: very powerful Google with memory.

Phase 2: Builder

The engineering phase

Hans shifted from answering to building. Writing real code deployed to real systems. The inspector app v1 → v100+. Google Apps Script. A client review portal. A scoring engine. Hans was now the engineering team.

Phase 3: Business OS

The operations phase

Hans became infrastructure. Team members (Tanner, Allie) can message Hans on Slack. Automated daily summaries. Scheduled background jobs. Memory that persists across sessions. Hans is no longer a tool — he's a team member.

Phase 4: AI Council

The coordination phase

Hans now coordinates with GPT (OpenAI's agent) in a shared Slack channel called #ai-council. Two AI systems collaborating on business problems, with Hans as the primary operator and GPT as a second opinion. A small company where the "team" includes multiple AI systems.

The inspector app wasn't in a roadmap — it got built because the field inspector needed a way to capture data offline. The Slack integration happened because team members were messaging Matt instead of being able to ask Hans directly. Real problems drove every expansion.

04 — Unique Applications

The unusual ways Hans is used

Most people use AI for writing help or answering questions. The way Hans is deployed goes significantly beyond that. Here are the genuinely unusual patterns.

📖

Persistent Memory Across Sessions

Hans maintains structured memory files that persist between conversations. Client details, project decisions, error patterns, team preferences — all written to disk. When Matt comes back a week later, Hans knows exactly where things stand. This is not how most people use AI.

🤝

Team-Facing Agent

Tanner (operations) and Allie (growth) can message Hans directly on Slack. Hans runs as a restricted agent for them — he can answer questions, look things up, and coordinate, but can't access sensitive context. One AI, two usage modes depending on who's asking.

⏰

Scheduled Background Jobs

Hans runs cron jobs — scheduled tasks that fire automatically. Daily summaries, reminder checks, context preservation. Hans can spawn isolated subagents that work in the background and report back. He works while Matt sleeps.

📋

Protocol Enforcement

Hans has built-in operating rules that prevent bad patterns. Three-failure hard stop (never make a fourth attempt). Session length monitoring. Banned words scanned in every reply. The AI enforces its own quality controls — the guardrails are in the files Hans reads at startup.

🔁

Reliability Fallback

The Mac mini runs a watchdog script. If OpenClaw crashes, it restarts within minutes. If the main internet tunnel goes down, a Hetzner server in Germany monitors and activates a backup tunnel automatically. Hans has uptime infrastructure like a production service.

🤖 + 🤖

AI-to-AI Collaboration

In the #ai-council Slack channel, Hans and GPT communicate directly. One AI asks another AI for a second opinion on business problems. Hans coordinates these sessions, sets the agenda, and synthesizes the output. This is genuinely novel territory.

The "heartbeat" system: Hans runs a periodic check-in called a heartbeat. It's a scheduled job that fires every 30 minutes or so. Hans checks a file called HEARTBEAT.md — if there are any checks listed there, he runs them (email scan, calendar check, etc.) and only reaches out if something needs attention. Most heartbeats are silent. This is how Hans stays useful without being annoying.

✍️

Copywriter / Content Strategist

🔬

Research Analyst

Strong replacement

Competitive analysis, pricing research, market sizing, technical audits — Hans does all of this. The competitive analysis that confirmed "nobody else combines a full test suite with scored reports" took one session and influenced the pitch deck.

🔧

DevOps / Systems Admin

Partial replacement

Hans manages the infrastructure config, monitors uptime, writes the watchdog scripts, manages the Cloudflare tunnel, and knows the SSH keys and Tailscale network. A real DevOps hire would do more, but Hans handles the basics that would otherwise need someone on call.

⚠️

What Hans cannot replace: Anything that requires being physically present, using a real phone browser, or authenticating as a human with a real account. Deploying a Google Apps Script update requires clicking through Google's browser UI — Hans cannot do this. Verifying something on an iPhone requires an iPhone. These are real limits and important to understand.

08 — Lessons Learned

What went wrong

This isn't a success story with no footnotes. There were real failures, some costly in time, some embarrassing, some that almost damaged the business. They're worth understanding.

🔴 The Photo Upload Disaster

Hans confirmed the inspection system was "ready." A real inspection happened. 42 photos from that inspection never uploaded to the client review portal. The upload filter code checked photo.imageData but photos were actually stored as photo.dataUrl — a one-field mismatch that was invisible until real data hit real code.

Lesson: Never sign off on a data pipeline without tracing the complete path from how data is stored → how it's extracted → how it's filtered → how it's sent → how it's confirmed. "The API is working" is not the same as "data is arriving."

🔴 The Apps Script Hour Loop

Hans sent Matt in circles for over an hour trying to redeploy a Google Apps Script update. What Hans should have said in the first 30 seconds: Apps Script deployments require a human to click through Google's browser UI. It cannot be automated. Instead, Hans kept trying variations until Matt was frustrated and time was wasted.

Lesson: State tool constraints and human-required steps before attempting anything. Never burn time on something fundamentally impossible with the tools available.

🟠 Stale Location Facts in Heartbeats

Heartbeat messages kept saying "Matt is in France" for weeks after he returned to Colorado. The AI was reading old memory facts and treating them as current. Location and availability facts were never flagged as expiring.

Lesson: Volatile facts (location, availability, what's "currently" happening) need expiry dates. Memory is only as good as the process for invalidating outdated entries.

🟠 Session Length Bloat

One session ran to 145,000 tokens — well past the point where context degradation was visible. Decisions made late in that session were influenced by incomplete context. A hard rule now exists: flag at 80K tokens, stop new topics at 120K.

Lesson: AI models have context windows. Long sessions don't just "slow down" — they degrade in quality as early context falls off. Enforce session length limits proactively, not after the damage is done.

🟡 The Gateway Token Incident

A configuration change caused a token mismatch that knocked out all remote access paths simultaneously — Tailscale was down, the Cloudflare tunnel was down, and Wi-Fi isolation blocked the LAN. Matt had to physically plug in a monitor to fix it. Total downtime: several hours.

Lesson: Before any infrastructure change, verify you have a recovery path that doesn't depend on the thing you're changing. Never lock all doors at once.

🟡 Fact Regression in Drafts

When Hans revised a document, he would sometimes regenerate content from scratch instead of making targeted edits. This reintroduced errors that had already been corrected. The rule now: patch, never regenerate. Every edit must be surgical on the existing file.

Lesson: AI has a tendency to "rephrase everything" when asked to revise. Force it to make targeted edits to existing content rather than rewriting from a blank slate.
📚

The meta-lesson: Every failure above got documented — in MEMORY.md, in CORRECTIONS.md, in AGENTS.md. The AI reads these files at the start of every session. Lessons compound. What went wrong in March doesn't happen again in July because it's written down and enforced. That's the actual advantage of a persistent agent over a stateless chatbot.

10 — Takeaways

What this means for you

If you're learning about AI and wondering what's actually possible, here are the honest takeaways from this real-world experiment.

🏗️

AI can build real software

Not toys. Not demos. A production app used by real inspectors on real jobs, iterated 146 times. The bottleneck is no longer whether AI can write code — it's whether you know what to build and how to verify it works.

🧠

Memory is the multiplier

A stateless chatbot is a powerful tool. An agent with persistent memory and access to real systems is something closer to a colleague. The memory architecture — what gets saved, when, and how it's loaded back — is what separates Hans from a chat window.

🚧

Limits are real and important

Hans can't click through a browser as a human. He can't verify what he can't see. He can't make judgment calls that require being physically present. Understanding where the edge of capability is — and designing your workflow around that edge — is the actual skill.

📋

Systems beat prompts

The one-sentence prompt is overhyped. What makes Hans reliable is the system around him: MEMORY.md, CORRECTIONS.md, AGENTS.md, protocol enforcement, session rules. The files Hans reads at startup are as important as the AI model itself.

⏩

Speed of iteration

Going from idea to deployed v1 in a weekend is genuinely new. The question is no longer "can we build this?" but "what should we build?" That's a fundamentally different problem — and a better problem to have.

🎓

The skill worth learning

The engineers who thrive with AI won't be the ones who fight it. They'll be the ones who know how to direct it, verify its work, understand where it fails, and build the systems that keep it reliable. That's the actual skill gap right now.
