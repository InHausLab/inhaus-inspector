Key Architectural Decisions

Vanilla JS, No Framework

No build step. Edit a file, push, deploys in seconds. Tradeoff: portal.js is 3,700+ lines with no module boundaries — hard to navigate at first.

PWA, Not Native App

Zero App Store delays. Updates on next Safari open. Works offline. Tradeoff: iOS kills background timers when phone locks. No reliable vibration.

Supabase for Photos

Replaced base64 → Apps Script → Drive which failed at scale (slow, unreliable, produced 178 duplicate folders in one incident). Supabase handles binary per-photo, idempotent uploads.

Cloudflare Workers

Edge speed, keeps Supabase service key private. Note: SYNC_SECRET and PHOTO_UPLOAD_SECRET are committed in config.js — visible to anyone with repo access. Not rotated.

Apps Script for Drive/Sheets

Only serverless path to Drive without OAuth complexity. Hard constraints: 6-minute execution limit per run, LockService queues concurrent submits, clasp breaks the web app URL.

What Breaks First

  • 🔒
    Apps Script LockService (most immediate) — 3+ inspectors submitting simultaneously queue behind a 30-second lock. Burst failures happen before weekly volume limits are reached.
  • ⏱️
    Apps Script 6-minute execution limit — A single large inspection (60+ photos, large JSON) can hit this at any volume. Symptom: submission silently fails, inspector gets no receipt.
  • 📁
    Drive folder scan timeout — Already confirmed at current test-folder volumes. Workaround is in place but not permanent.
  • 🖼️
    Drive photo mirror is best-effort, not guaranteed — If the CF Worker /mirror call times out or hits Drive rate limits, photos exist in Supabase but are permanently absent from Drive. At 2,000–5,000 photos/week this becomes a real failure mode.
  • 👤
    Single Drive account (Matt's personal) — All data is in Matt's personal Google account. One failure point, shared quota. Must move to Shared Drive before handoff is real.

Critical Rules

Every one of these exists because something broke without it.
🚨
Rule 0 — Do not deploy Apps Script HEAD to production right now v87 is the repo HEAD. v86 is what's live. v87 broke review reads. Do not paste Code.gs into the editor and deploy until the review-read path is rebuilt and verified. This will break active inspections.
  1. Never deploy Apps Script via clasp Clasp changes the web app deployment URL, which breaks the live app. Always paste Code.gs into the editor UI and deploy as a new version. This is the only safe path.
  2. Always edit Code.gs in the repo first, then deploy The Apps Script editor was wiped July 20 and v52–v64 were lost permanently. The GitHub repo is the source of truth. Never edit the editor directly.
  3. CHANGELOG.md is the engineering ground truth Update it every time something changes. When handing to Codex, include it. This document is a summary — CHANGELOG has the full detail including known regressions and open debt.
  4. Verify every Apps Script deploy with a POST, not GET GET success does not mean POST works. Run the curl command in CHANGELOG.md. Must return {"status":"ok",...}. A GET-only check has caused missed failures before.
  5. Photos are the highest-risk component Before any inspection or demo, trace the full path: capture → Supabase upload → Drive mirror → Photo Log. Do not call the system ready based on endpoint checks alone. The Drive mirror is best-effort — photos can be in Supabase but absent from Drive.
  6. Bump CACHE_NAME on every version that changes app behavior iOS Safari PWA instances cache aggressively. If you push a change without bumping CACHE_NAME in service-worker.js, Dave's phone won't get the update until he closes all tabs and reopens. Every significant release needs a cache bump.
  7. All photo queries must filter tombstoned records Deleted photos are not hard-deleted from inspector_photo_uploads. They're tombstoned with source_system='deleted'. Any new query that reads photos without this filter will resurrect deleted photos. Filter: WHERE source_system != 'deleted'
